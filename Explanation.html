Phase 00

Skeleton

No game yet — a workshop, built and checked, with the tools laid out and the rules already enforced.

What we were trying to do

Before building anything you want a bench, good light, and a way of telling whether what you have made is any good. That is all this piece of work was. We set up the workshop: the machine that turns what we write into something a browser can show, a way of running tests, and a single command that checks everything at once and refuses if anything is wrong.

The only thing on screen at the end of it is a flat grey plane lit orange, like an empty road under a streetlight, with a small readout in the corner counting how fast the picture is being redrawn. That is deliberate. There is no motorbike, no track and no race. What there is, is a room where the next ten pieces of work can happen without anyone tripping over anything.

Why this was hard

Honestly, it wasn't very. Setting up tools is a solved problem and most of a day's difficulty is looking things up. Saying otherwise would be manufacturing drama.

There is one thing that was genuinely awkward, though, and it is a strange one: we had to build the alarms before there was anything to protect. This project has six rules it must never break — one of them is that the part of the code that decides what happens in a race must never be allowed to touch the part that draws pictures. We wanted a machine that refuses to accept work that breaks that rule. But the part that decides what happens in a race does not exist yet. So we were writing a burglar alarm for an empty house, with no way to know whether it would go off.

The same problem hit the test that measures how much of the code is checked by other tests. We told it to demand that 80% of the simulation is covered. There is no simulation. It looked at nothing, found nothing wrong with nothing, and passed. That is worse than failing, because a rule that has never once said no is indistinguishable from a rule that does not work. So the real work here was proving the alarms ring: deliberately writing bad code, watching each check reject it, and then deleting it again.

What we tried that didn't work

A test that could never have caught anything

The corner readout keeps the last 120 frame times and reports the worst ones, so a stutter shows up even when the average looks healthy. To find the worst, it sorts the numbers. There is a famous trap here: in JavaScript, sorting a plain list of numbers sorts them as if they were words, so 100 lands before 9. We wrote a test to guard against exactly that, fed it 95 fast frames and 5 slow ones, and asserted the slow number came out. It failed.

Two wrong beliefs in one test, and the code was right both times. First, the numbers are not kept in a plain list but in a fixed-size numeric one, and that kind sorts numerically already — the trap we were guarding against cannot happen here, so the test was incapable of catching anything. Second, the answer we demanded was wrong anyway: with exactly 95 out of 100 frames fast, the "95% mark" genuinely is a fast frame. We had confidently written a test that was wrong twice and would have felt reassuring if it had passed.

Starting on a toolchain with known holes in it

We first pinned the versions of the build tools that were current when the project was sketched out. Installing them reported six security problems, two of them rated critical. All six came from one small program buried underneath everything else, which had a flaw letting any website you visited talk to the private server running on your own machine and read what came back.

Not a coding mistake — a starting-point mistake. The flaw only affects the development machine and could never reach a player. It is tempting to leave it. But this project has ten more phases to run, and there was nothing built yet that depended on those old versions, so the cost of moving was zero and the cost of staying was ten phases of running a server we knew was leaky. Upgraded; the report is now clean.

A rule that silently switched off fifty others

One small script does not go into the game and does not need the strictest checks, so we told the checker to relax them for that file, then added one preference of our own on the next line. The whole thing crashed, complaining it had been asked to apply a deep check to a file it knew nothing about.

Adding our one preference did not add it to the list of relaxations — it replaced the entire list. Fifty rules we had just switched off came straight back on. The fix was one line, but it is a good example of the kind of mistake that produces a completely misleading error message: nothing in the words "you have used a rule which requires type information" points at the thing that actually went wrong.

What we went with, and why

One command, npm run check, that runs four different kinds of check in sequence and fails the moment any of them complains: does the code make sense on its own terms, does it follow the house style and the project's rules, do the tests pass with enough of the important code actually exercised, and is the finished download still small enough. The same command runs on our machine and on the server after every change, so there is no such thing as "works for me".

We also chose to make the checks harsh now rather than later. Every optional strictness setting is on, the size limit is measured rather than estimated, and the coverage rules stop the build rather than printing a warning nobody reads.

What this costs: friction, every single day, starting immediately. Turning these on later would be far more pleasant than living with them from the first commit — but turning them on later is a job that never gets done, because by then there are two hundred violations and no appetite. We are paying a small tax constantly to avoid a large bill we would never actually pay.

We didn't use a game engine — Unity, Godot, Unreal — because this game needs almost nothing they provide. It is a road, some riders, and arithmetic. The engine would bring a physics system we have deliberately decided not to use, a scene editor for a world we generate from data, and a download tens of times larger than the entire budget for this one. We didn't use a physics library for the same reason: the riding model here is tuned by feel, not simulated, which is the right choice for an arcade racer and is covered on the Phase 2 page.

Show me in the code

src/ui/FrameMeter.ts → stats()

This is the corner readout's arithmetic, and the place the worst mistake of the phase was hiding. Line numbers below refer to the block as printed here. 

  stats(): FrameStats {
    if (this.count === 0) {
      return { fps: 0, meanMs: 0, worstMs: 0, p95Ms: 0, overBudget: 0 };
    }

    let total = 0;
    let worst = 0;
    let overBudget = 0;
    for (let i = 0; i < this.count; i += 1) {
      const ms = this.samples[i] ?? 0;
      total += ms;
      if (ms > worst) worst = ms;
      if (ms > BUDGET_MS) overBudget += 1;
      this.sorted[i] = ms;
    }

    const window = this.sorted.subarray(0, this.count);
    window.sort();

    const meanMs = total / this.count;
    const p95Index = Math.min(this.count - 1, Math.ceil(this.count * 0.95) - 1);

    return {
      fps: meanMs > 0 ? 1000 / meanMs : 0,
      meanMs,
      worstMs: worst,
      p95Ms: window[p95Index] ?? worst,
      overBudget,
    };
  }
  1. Line 10. ?? 0 looks like superstition and isn't. noUncheckedIndexedAccess makes TypeScript treat every array lookup as possibly missing, so this is the compiler forcing an answer for a case that cannot occur here. That is the deal we signed when we turned it on.
  2. Lines 6–15. One pass computes the total, the worst, and the count over budget, and copies into the scratch buffer at the same time. Four passes would read better; this runs on every readout and the buffer is reused rather than allocated.
  3. Lines 17–18. subarray is a view over the existing buffer, not a copy — so this sorts in place and allocates nothing. And because it is a Float64Array, sort() is numeric. On an ordinary array it would sort as text and 100 would come before 9.
  4. Line 21. The line that produced the failing test. ceil(n × 0.95) − 1 is nearest-rank: with 100 samples it points at the 95th, which with 95 fast frames is still a fast frame. That is correct, and there is now a test asserting it deliberately so nobody "fixes" it later.
  5. Line 27. worst as the fallback rather than zero: if the index were ever wrong, the readout would report something alarming rather than something reassuring. Failures should be loud.

Say it out loud

Phase zero is scaffolding, so the interesting part isn't the stack — it's Vite, TypeScript, Vitest, ESLint, and Three.js, which is the boring correct answer. The interesting part is that the gates had to be built before the code they guard, so I proved each one fires instead of assuming it: I dropped a deliberately undertested file into the simulation folder, watched both coverage thresholds reject it independently, and deleted it. That also caught the one real mistake of the phase — a percentile test I'd written to guard against lexicographic sorting in a Float64Array, which sorts numerically, so the test couldn't have caught anything, and I'd got the nearest-rank boundary wrong on top. The bundle is 117 KB gzipped against a 500 KB budget that's measured on every run and doesn't grow.

In 90 seconds

Where the project stands after Phase 0, and the decisions carrying the most weight.

The elevator version

Rashta is an arcade motorcycle combat racer set on Delhi's ring roads at night — fourteen riders, point-to-point, no rules. The interesting idea is that nothing in the simulation knows where it is in the world. Every rider stores two numbers: how far along the road they are, and how far sideways. Who's winning becomes a comparison of two numbers instead of a geometry problem, and the whole race can be replayed exactly from a seed. Positions in actual space are worked out only when something has to be drawn. Right now the workshop is built and proven — the build, the tests, the rules that stop the architecture eroding — and the road itself arrives next.

The three decisions that most shaped the project

  1. Everything positional lives in track space. A rider is two numbers — metres along the centreline, metres sideways from it — never an x, y, z. World position is derived at render time and stored nowhere.

    Why: it turns the hard questions into arithmetic. Who's ahead, am I on the road, spawn a bus 300 m up — each is a comparison rather than a geometry query. It is also what makes the simulation pure, testable, and cheap to replay.

    Cost: the road can never cross itself, fold back, or branch freely, and free-roam is impossible. Forks are explicit machinery rather than something the geometry gives us. For a point-to-point racer, an easy trade.

  2. The simulation is bit-exactly deterministic, and that constrains the arithmetic it may use. Same seed plus same inputs gives the same race on any machine. All randomness goes through one seeded generator — and, less obviously, no sine, cosine, or power function is allowed anywhere in the simulation.

    Why: the floating-point standard pins add, subtract, multiply, divide, and square root to identical results on every engine, but deliberately leaves the trigonometric functions to the implementation. A single cosine in the simulation quietly downgrades "the same everywhere" to "the same here". Trigonometry is confined to loading the track and to drawing.

    Cost: real work, permanently. Anything needing angles has to be precomputed into tables and interpolated, and the distance function had to be built as an approximation rather than the exact formula. It bought reproducible races, which is the difference between debugging balance and guessing at it.

  3. No engine, no framework, no physics library. The runtime dependency list is one item long: Three.js, for drawing.

    Why: this game is a road, some riders, and arithmetic. An engine would supply a physics system we have deliberately rejected in favour of a hand-tuned arcade model, an editor for a world we generate from data, and a download many times our entire budget.

    Cost: we write things engines give away — the road mesh, the camera, the object pooling, the save system. Every one of those is a phase that could have been free. The return is a 117 KB download and a codebase where nothing happens that we did not write.
