Phase 00

Skeleton

No game yet — a workshop, built and checked, with the tools laid out and the rules already enforced.

What we were trying to do

Before building anything you want a bench, good light, and a way of telling whether what you have made is any good. That is all this piece of work was. We set up the workshop: the machine that turns what we write into something a browser can show, a way of running tests, and a single command that checks everything at once and refuses if anything is wrong.

The only thing on screen at the end of it is a flat grey plane lit orange, like an empty road under a streetlight, with a small readout in the corner counting how fast the picture is being redrawn. That is deliberate. There is no motorbike, no track and no race. What there is, is a room where the next ten pieces of work can happen without anyone tripping over anything.

Why this was hard

Honestly, it wasn't very. Setting up tools is a solved problem and most of a day's difficulty is looking things up. Saying otherwise would be manufacturing drama.

There is one thing that was genuinely awkward, though, and it is a strange one: we had to build the alarms before there was anything to protect. This project has six rules it must never break — one of them is that the part of the code that decides what happens in a race must never be allowed to touch the part that draws pictures. We wanted a machine that refuses to accept work that breaks that rule. But the part that decides what happens in a race does not exist yet. So we were writing a burglar alarm for an empty house, with no way to know whether it would go off.

The same problem hit the test that measures how much of the code is checked by other tests. We told it to demand that 80% of the simulation is covered. There is no simulation. It looked at nothing, found nothing wrong with nothing, and passed. That is worse than failing, because a rule that has never once said no is indistinguishable from a rule that does not work. So the real work here was proving the alarms ring: deliberately writing bad code, watching each check reject it, and then deleting it again.

What we tried that didn't work

A test that could never have caught anything

The corner readout keeps the last 120 frame times and reports the worst ones, so a stutter shows up even when the average looks healthy. To find the worst, it sorts the numbers. There is a famous trap here: in JavaScript, sorting a plain list of numbers sorts them as if they were words, so 100 lands before 9. We wrote a test to guard against exactly that, fed it 95 fast frames and 5 slow ones, and asserted the slow number came out. It failed.

Two wrong beliefs in one test, and the code was right both times. First, the numbers are not kept in a plain list but in a fixed-size numeric one, and that kind sorts numerically already — the trap we were guarding against cannot happen here, so the test was incapable of catching anything. Second, the answer we demanded was wrong anyway: with exactly 95 out of 100 frames fast, the "95% mark" genuinely is a fast frame. We had confidently written a test that was wrong twice and would have felt reassuring if it had passed.

Starting on a toolchain with known holes in it

We first pinned the versions of the build tools that were current when the project was sketched out. Installing them reported six security problems, two of them rated critical. All six came from one small program buried underneath everything else, which had a flaw letting any website you visited talk to the private server running on your own machine and read what came back.

Not a coding mistake — a starting-point mistake. The flaw only affects the development machine and could never reach a player. It is tempting to leave it. But this project has ten more phases to run, and there was nothing built yet that depended on those old versions, so the cost of moving was zero and the cost of staying was ten phases of running a server we knew was leaky. Upgraded; the report is now clean.

A rule that silently switched off fifty others

One small script does not go into the game and does not need the strictest checks, so we told the checker to relax them for that file, then added one preference of our own on the next line. The whole thing crashed, complaining it had been asked to apply a deep check to a file it knew nothing about.

Adding our one preference did not add it to the list of relaxations — it replaced the entire list. Fifty rules we had just switched off came straight back on. The fix was one line, but it is a good example of the kind of mistake that produces a completely misleading error message: nothing in the words "you have used a rule which requires type information" points at the thing that actually went wrong.

What we went with, and why

One command, npm run check, that runs four different kinds of check in sequence and fails the moment any of them complains: does the code make sense on its own terms, does it follow the house style and the project's rules, do the tests pass with enough of the important code actually exercised, and is the finished download still small enough. The same command runs on our machine and on the server after every change, so there is no such thing as "works for me".

We also chose to make the checks harsh now rather than later. Every optional strictness setting is on, the size limit is measured rather than estimated, and the coverage rules stop the build rather than printing a warning nobody reads.

What this costs: friction, every single day, starting immediately. Turning these on later would be far more pleasant than living with them from the first commit — but turning them on later is a job that never gets done, because by then there are two hundred violations and no appetite. We are paying a small tax constantly to avoid a large bill we would never actually pay.

We didn't use a game engine — Unity, Godot, Unreal — because this game needs almost nothing they provide. It is a road, some riders, and arithmetic. The engine would bring a physics system we have deliberately decided not to use, a scene editor for a world we generate from data, and a download tens of times larger than the entire budget for this one. We didn't use a physics library for the same reason: the riding model here is tuned by feel, not simulated, which is the right choice for an arcade racer and is covered on the Phase 2 page.

This is the corner readout's arithmetic, and the place the worst mistake of the phase was hiding. Line numbers below refer to the block as printed here. 

  stats(): FrameStats {
    if (this.count === 0) {
      return { fps: 0, meanMs: 0, worstMs: 0, p95Ms: 0, overBudget: 0 };
    }

    let total = 0;
    let worst = 0;

      total += ms;

      if (ms > BUDGET_MS) overBudget += 1;

    window.sort();

    const meanMs = total / this.count;
    const p95Index = Math.min(this.count - 1, Math.ceil(this.count * 0.95) - 1);

    return {
      fps: meanMs > 0 ? 1000 / meanMs : 0,
      meanMs,
      worstMs: worst,
      p95Ms: window[p95Index] ?? worst,
      overBudget,
    };

  1. Line 10. ?? 0 looks like superstition and isn't. noUncheckedIndexedAccess makes TypeScript treat every array lookup as possibly missing, so this is the compiler forcing an answer for a case that cannot occur here. That is the deal we signed when we turned it on.
  2. Lines 6–15. One pass computes the total, the worst, and the count over budget, and copies into the scratch buffer at the same time. Four passes would read better; this runs on every readout and the buffer is reused rather than allocated.

  5. Line 27. worst as the fallback rather than zero: if the index were ever wrong, the readout would report something alarming rather than something reassuring. Failures should be loud.

Say it out loud

Phase zero is scaffolding, so the interesting part isn't the stack — it's Vite, TypeScript, Vitest, ESLint, and Three.js, which is the boring correct answer. The interesting part is that the gates had to be built before the code they guard, so I proved each one fires instead of assuming it: I dropped a deliberately undertested file into the simulation folder, watched both coverage thresholds reject it independently, and deleted it. That also caught the one real mistake of the phase — a percentile test I'd written to guard against lexicographic sorting in a Float64Array, which sorts numerically, so the test couldn't have caught anything, and I'd got the nearest-rank boundary wrong on top. The bundle is 117 KB gzipped against a 500 KB budget that's measured on every run and doesn't grow.

Phase 01

Track space

The road, as pure arithmetic. No graphics at all — if this is wrong, everything built on top of it is wrong, and a screen would never tell you.

What we were trying to do

Think about how you'd describe where you are on a motorway. You wouldn't give someone a map reference. You'd say "eleven miles along, in the middle lane". Two numbers, both about the road rather than about the world.

That is exactly how this game stores every rider, every bus, every stray dog: how far along the road they are, and how far sideways from the middle. Their actual place in space is worked out only at the last moment, when something has to be drawn on screen.

This piece of work built that idea and nothing else. Describe a road as a list of pieces — this much straight, then a bend of this tightness, then a slope. Work out, for any distance along it, where that point sits, which way the road faces there, how wide it is. Check that two riders can be compared even when the road splits in two and rejoins. There is nothing to look at when it is finished, which is the point: a wrong road would look perfectly convincing.

Why this was hard

Two rules pulled against each other, and both were fixed.

The first is that a replay must come out identical on every machine. Same starting number, same button presses, same race — on your laptop, on someone's phone, in five years. That is what makes a bug reproducible instead of a story someone tells you.

The second is geometry. Working out where you are on a bend is a question about circles, and questions about circles are answered with sine and cosine — the two functions every schoolchild meets in trigonometry.

Here is the collision. Computers agree exactly on what plus, minus, times, divide and square root produce, down to the last digit — there is an international standard that says so. Sine and cosine are not on that list. Two browsers can return answers that differ in the sixteenth decimal place, and neither is wrong. Feed that into a race sixty times a second for eight minutes and the two machines are watching different events.

So the geometry needed trigonometry and the guarantee forbade it. That is the whole phase.

What we tried that didn't work

Measuring distance the obvious way, and only testing it in one direction

Riders need to know how far apart they are — to throw a punch, to avoid a bus. On a bend that is not as simple as it sounds, because the inside of a bend is shorter than the outside, so "two metres along the road" means different real distances depending which side you are on. We had a correction for that, and it was tested carefully across the full width of the road. It passed.

Then the same correction was tested with the riders further apart along the road rather than across it, and the error was nine times over budget. The testing had swept one direction thoroughly and quietly held the other one fixed at a single value — so a whole axis of the problem had never been looked at. The same mistake had been made once already earlier in the project, on the same function, in the other direction.

A test that said the road was broken, and was right

A test checked that the road never jumps — that walking a millimetre forward moves you a millimetre, with no sudden skips. Position passed. But the direction the road faces failed, jumping abruptly at one join.

The number in the failure was 0.04995, and the slope of the hill in the test road was 0.05. Not a coincidence. Tightness of a bend and steepness of a hill look like the same kind of setting in a road description, sitting side by side in the file, but they behave completely differently: bend tightness gets added up gradually into a direction, so it smooths itself out, while steepness is the direction, so changing it is a sudden kink — a hilltop with no rounding at all. Real roads solve this with a gradual crest. We kept the kink, wrote a test that pins it in place, and left a note explaining why, so that anyone who later decides to "fix" it has to argue with a test first.

A safety check that was mostly for show

One test scans the simulation's code looking for the forbidden functions, so the rule is enforced by machine rather than by memory. It failed, reporting that the random number generator used a mathematical operator it does not contain.

The scan was reading the explanatory notes written above the code as though they were code. The symbol that opens a comment block happens to look like the symbol for "raise to the power of". Which meant the whole check was inspecting English prose alongside instructions — and it had been passing partly by luck, since one file contains a note that literally names a banned function while explaining that it is banned. Now it strips the notes out before looking.

A tidy-looking function that nothing used

Everything passed, but the requirement that every line of this code be exercised by a test came up one line short. The uncovered line was a small function reporting the length of a stretch of road.

Nothing called it. Not the tests, not the rest of the code, and no part of the plan had asked for it — it had been written because it seemed like something a road ought to offer. Rather than write a test to justify it, we deleted it. Worth noticing that a strict requirement is what surfaced it; a looser one would have let it sit there for years.

What we went with, and why

The trigonometry happens exactly once, when the road is first loaded, and never again. Loading walks the road and works out several thousand fixed reference points along it — position, facing, width — and stores them in a flat table. Afterwards, asking about any point on the road is a fast lookup of the two nearest stored points and a blend between them. That is only adding, multiplying and dividing, so it is identical on every machine.

That's called a lookup table with linear interpolation: precomputing an expensive function at fixed intervals and approximating intermediate values from the neighbouring samples. The spacing between samples is not a guess — it is derived from how far a straight line can stray from a curve, so tight corners get samples every 25 cm and gentle ones every 2 metres.

For measuring distance between riders, we did something better than approximating. Writing the exact answer out algebraically, most of it collapses into ordinary arithmetic, and exactly one sine remains. That single sine is replaced with a Maclaurin series — a way of rewriting a curved function as a short sum of powers, which is pure multiplication. Four terms of it, and the answer matches the true geometry to about one part in ten million.

What this costs: memory and load time. A long track holds tens of thousands of stored numbers that a live calculation would not need, and building them is work done before the race can start. For a 28 km road that is under a megabyte and imperceptible, but it is a real cost, paid to buy the guarantee.

We didn't use the obvious alternative — just calling sine and cosine whenever we need them, and accepting that replays only hold on one machine — because the entire reason the simulation is built the way it is, separate from the graphics and driven by a fixed clock, is so that a race can be reproduced exactly. Give up cross-machine reproducibility and most of that structure stops earning its keep.

The constraint turned out to improve the result rather than compromise it. Being forbidden the easy tool forced the distance formula to be written out properly, which is where a simplification appeared that nobody was looking for. With sine available we would have shipped the rougher version and never found it.

Show me in the code

src/core/track/distance.ts → trackDistance()

How far apart two riders really are, in metres, on a bending road — without a single forbidden function. 

export function trackDistance(a: TrackPos, b: TrackPos, track: Track): number {
  if (a.branchId !== b.branchId) return Number.POSITIVE_INFINITY;

  const ds = b.s - a.s;
  const dt = b.t - a.t;

  const midS = (a.s + b.s) / 2;
  const curvature = track.curvatureAt(midS, a.branchId);
  if (curvature === 0) return Math.sqrt(ds * ds + dt * dt);

  // Clamp to the road before correcting. Validation guarantees `1 - t * k`
  // stays positive within halfWidth + shoulder; a rider who has left the road
  // entirely is off the geometry this describes and should get a sane
  // distance rather than a negative radius.
  const limit = track.driveableHalfWidthAt(midS, a.branchId);
  const ta = clamp(a.t, -limit, limit);
  const tb = clamp(b.t, -limit, limit);

  const radius = 1 / Math.abs(curvature);
  const ra = radius * (1 - ta * curvature);
  const rb = radius * (1 - tb * curvature);

  const sweep = Math.abs(ds) * Math.abs(curvature);
  const along = Math.sqrt(ra * rb) * sweep * chordOverArc(sweep);

  return Math.sqrt(along * along + dt * dt);
}
  1. Riders on different sides of a fork can never touch, so they are infinitely far apart. That is the answer combat and collision actually want, and it falls out of the road model rather than needing a special case.
  2. On a straight, this is the flat-earth answer — the one everyone expects. Everything below only matters because roads bend.
  3. A rider who has flown off the road entirely is outside the geometry this formula describes. Clamping keeps them at the road's edge, so the answer stays sensible instead of going negative.
  4. The heart of it: a point sitting t metres to the side of a bend of tightness k is riding a circle of a different size to the one down the middle. The inside of the bend is a smaller circle, so the same distance along the road covers less ground.
  5. Multiplying the two radii and taking the square root — rather than averaging them — is not a nicety. It is what the exact algebra produces, and it is where the naive version lost most of its accuracy.
  6. chordOverArc is the banned sine, rewritten as four multiplications. This one line is the difference between a replay that holds on every machine and one that holds only on the machine that recorded it.

Say it out loud

Everything in the simulation lives in track space — distance along the centreline and lateral offset — so world coordinates only exist at render time. The hard constraint was that the simulation has to be bit-exactly deterministic across machines, and IEEE-754 doesn't pin the transcendentals, so sine and cosine are banned from anything the step function reaches. Track sampling solves that by doing all the trigonometry once at load into a table whose spacing is derived from the arc's sagitta, then interpolating linearly between nodes. For distance between riders I wrote the exact chord out algebraically, which collapses to dt squared plus four r-one r-two sine-squared of half the sweep, and replaced just the sine with a four-term Maclaurin series. That reads to about one part in ten million against the exact geometry, and the whole thing is arithmetic the standard pins exactly. The road code sits at a hundred percent line coverage, and a test asserts no transcendental is reachable from the simulation, because that rule is the one nothing else can enforce.

Phase 02

The feel gate

One bike, one straight road, and a camera behind it. The only question that matters is whether riding is enjoyable before anything is at stake.

What we were trying to do

Up to now there was a road but nothing on it. This piece of work put a motorbike on that road and made it possible to ride.

That means three separate things. Something has to decide how fast the bike goes when you hold the accelerator, and how it moves across the road when you steer. Something has to read the keyboard or the controller and turn presses into those instructions. And something has to draw it — the road surface, the streetlights, the kerb, the bike, and a camera sitting behind your shoulder.

The road is deliberately a straight line, with nothing on it and nowhere to go. That sounds like a strange thing to spend a whole stage of work on, and it is the entire point: if riding in a straight line with nothing happening is not already enjoyable, no amount of rivals or fighting or scenery added later will rescue it. So this is a gate, not a feature. Either it feels good and the project continues, or it does not and we stop and fix it.

Why this was hard

The difficulty is that "how fast is this bike" has four different honest answers and they contradict each other.

A bike in the data file has an engine power, a weight, a top speed, and a description of how its acceleration is spread out across its speed range. In the real world any three of those determine the fourth. So if someone writes all four down by hand, sooner or later two of them disagree — and the disagreement does not announce itself. It shows up as a bike that says 200 km/h on the stat sheet and does not do 200 km/h, and a tuning session spent adjusting the wrong number.

Divyansh settled this before any code was written by fixing which number is allowed to be the truth for which quality: top speed owns the ceiling, a separate stated time owns how long the bike takes to get there, the acceleration shape describes only the distribution along the way, weight affects only cornering and shoving, and engine power is display text the simulation is forbidden from reading.

That is a clean rule and it creates a real problem. If the shape carries no magnitude of its own, then doubling every number in it must change the character of the acceleration and leave the time to top speed exactly unchanged. The shape cannot be used as acceleration directly. Something has to work out the right scale for it, from the other two numbers, for every bike.

What we tried that didn't work

A test that reported nonsense because it looked in the wrong place

The test that checks each bike reaches its stated top speed in its stated time reported "not a number" for all three bikes. Both sides of the comparison were meaningless, so the failure said nothing about where the fault was.

Printing the bike's state every few hundred steps showed the speed climbing perfectly smoothly and settling exactly on the right figure. The simulation was correct; the measurement was wrong. The test was asking the rider how many steps had elapsed, and the step count is kept on the world, not on the rider. Asking for something that isn't there gives "undefined", and arithmetic on that gives "not a number". The type checker would have caught this instantly, but the quick way of running a single test file skips the type check — so the fast loop is genuinely weaker than the full one, which is worth knowing.

Demanding exactness from a system built out of inexactness

A test fed the clock ten seconds' worth of frames from a fast 144-frames-a-second monitor and checked that exactly 600 simulation steps came out. It got 599.

Not a bug — the test was wrong. A computer cannot store "one 144th" precisely, in the same way you cannot write out a third as a decimal without stopping somewhere. Add up 1440 of those slightly-short pieces and you land a whisker under ten seconds, and the last step genuinely has not fallen due. The leftover is kept rather than thrown away, so this never accumulates. We replaced it with the property actually worth guaranteeing: run ten minutes and land within one step of correct.

The recycling streetlights, wrong twice for different reasons

Roadside objects are not created and destroyed as you ride past — a fixed set is reused, with whatever falls behind you moved round to the front. Both times we got the arithmetic of "moved round" wrong. First the kerb developed gaps; then, after fixing that, a single streetlight kept flickering out of existence.

The first was straightforward: objects sit on both sides of the road, so there are two of them per position, and the code moved things by the count of objects instead of the count of positions — twice as far as it should. The second was subtler. Each set deliberately holds one spare beyond what you can see, so nothing pops into view at the horizon. That makes the loop of positions longer than the visible stretch, so one of them has nowhere legal to sit and got bounced back and forth every frame. The fix was to stop thinking of it as "keep it in view" and treat it as what it actually is — a remainder, wrapped into a window of exactly the right size.

Three pieces of litter a frame, in the worst possible place

No test caught this one; it was spotted rereading the code. The camera created three small throwaway objects every single frame to convert between the simulation's own maths and the graphics library's. That is 180 pieces of litter a second.

Worth recording precisely because nothing failed. The game would have run, and the automatic cleanup would have absorbed it, and it would have surfaced at the very end of the project as an unexplained periodic stutter during the long soak test — by which point the cause is a needle in a haystack. It is in the one function guaranteed to run every frame, in the file whose whole purpose is the thing the no-litter rule exists to protect.

What we went with, and why

The scale for each bike's acceleration is solved, not tuned. Write down that the time taken is the whole speed range divided by the acceleration at each point, and the answer falls out: the scale equals the top speed, multiplied by a single number summarising the shape, divided by the stated time. That summary number is worked out once when the bike is loaded.

That's a definite integral evaluated with Simpson's rule, and it gives the property the design demanded for free: doubling every entry in the shape halves the summary number and doubles the scale, leaving the time to top speed identical. Every bike arrives at its advertised speed in its advertised time by construction, not by adjustment.

The riding itself is an arcade model, not a physics simulation. A rider is five numbers, and only two of them — speed along the road and speed sideways — actually move anything. Steering asks for a sideways speed rather than setting one, and the amount it can ask for shrinks as you go faster, which is what makes the bike feel heavy at speed without simulating any actual weight.

What this costs: everything that would emerge from real physics has to be faked or forgone. No weight shifting under braking, no wheelies, no front wheel washing out on a bad line — and a gearbox that exists only in the dial, because the simulation has one continuous speed with no gears in it at all.

We didn't use a physics engine, which is the obvious alternative and would have given all of that away free, because an arcade racer wants a bike that responds the way the player expects rather than the way a rigid body would. Tuning a physics engine to feel arcadey is harder than writing an arcade model, and it would cost more download than the entire game currently weighs.

One more decision worth naming: the simulation cannot see a clock. It advances in identical steps of one sixtieth of a second, and the piece that decides how many steps to run is handed elapsed time by whoever calls it. That is what lets a test replay the same recorded button presses against a deliberately erratic clock — anywhere from 240 frames a second down to 12 — and get a bit-for-bit identical result.

src/core/sim/bike.ts → tuneBike()

Nine lines that make the whole authority split work: turning a shape with no magnitude, plus a top speed, plus a stated time, into the one constant the simulation integrates. 

export function tuneBike(spec: Bike, integralSlices: number): TunedBike {
  const topSpeedMs = spec.topSpeed * KMH_TO_MS;
  const integral = inverseCurveIntegral(spec.accelCurve, integralSlices);
  return {
    spec,
    topSpeedMs,
    accelScale: (topSpeedMs * integral) / spec.timeToTopSpeed,
  };
}
  1. The data file is written in km/h because that is what a person reading a stat sheet expects; the simulation works in metres per second. Converting once, here, means the conversion never appears in the loop where it could drift.
  2. The one number that summarises the shape. It depends only on the curve, so it is computed once per bike at load rather than sixty times a second.
  3. The entire solve, and the reason the design rule holds. Double every entry in accelCurve and integral halves, so accelScale doubles, so the time to top speed is unchanged — which is exactly what "the shape carries no magnitude" has to mean. A test asserts it rather than trusting the algebra.

Say it out loud

The bike's an arcade model — five scalars per rider, and only speed and lateral velocity actually integrate. The interesting bit is the acceleration solve. Speed, power, mass and acceleration over-determine a vehicle, so we fixed an authority split in the design doc: topSpeed owns the ceiling, timeToTopSpeed owns the magnitude, and accelCurve is shape only. That means the curve can't be read as acceleration directly — you write the time as the integral of dv over K times f of u, solve for K, and you get K equals vmax times the integral of one over f, over T. Simpson's rule at load, once per bike. Doubling the curve halves the integral and doubles K, so the time to top speed is invariant, which is the property the split actually needs, and there's a test on it. The loop is a fixed sixtieth of a second with render interpolation, and the accumulator never touches a clock — the caller passes elapsed time in, so a replay test can jitter the wall clock from 240 hertz to 12 and still get a bit-identical world.

Phase 03

Real tracks

Five Delhi routes, each five times over, with roads that split in two and rejoin — and five districts that look nothing like each other.

What we were trying to do

Until now there was one road, and it was a straight line twenty kilometres long. This was the piece of work that replaced it with actual places.

Five routes across Delhi, each with its own character: a dark forested ridge, a wide riverside road, a busy multi-lane ring road, a cramped old-city warren, and an elevated expressway with nothing at all on one side. Each of those exists at five difficulty levels, where each level is the previous one carried further rather than a different road — so twenty-five races in total.

Two harder things came with them. Each route splits in two at least twice, so you can choose a way round and neither choice is simply better. And each district had to actually look different — how far you can see, what colour the light is, how close the fog sits.

Why this was hard

A road that splits and rejoins has to satisfy two demands that pull against each other, and both are absolute.

The first is that the detour must arrive back exactly where it left. Not nearly — the two roads join, so if the loop comes back three metres sideways of where it claims to, riders merge into thin air and there is nothing on screen to explain why.

The second is that the two ways round must be close to the same length. If one is meaningfully shorter, it isn't a choice — it's an arithmetic problem with one right answer, and every rider takes the same road every time. The design brief allows five percent.

Those two together are a real constraint. Any curved detour that returns to its own starting line is automatically longer than the straight it replaced, because a curve is longer than its chord. How much longer depends on how sharply it bends. So the shape can't be drawn by eye and adjusted until it looks right — the bend angle and the distance have to be solved together, ten times over.

And then a separate problem hiding underneath: what does it even mean to be "ahead" of someone taking the other road?

What we tried that didn't work

The slip road came off the middle of the carriageway

The rule for taking a fork is: drift toward the side the road peels off, and you're on it. The first test held the bike hard right down the Ring Road, straight past a right-hand slip road, and it never took it.

Both roads of a split were being built from the same centre line, so the slip road's mouth was in the middle of a twenty-six-metre carriageway rather than at its edge. A rider pinned to the right-hand kerb was thirteen metres from a road only seven metres wide — and a check added moments earlier, correctly stopping riders from being yanked sideways as they entered, refused them. Two things wrong in the same way: a slip road leaves from the edge of the road it leaves. Once branches knew how far to the side they start, entry became a shift of viewpoint rather than a jump, and a rider on the outside edge of a wide road is exactly on the outside edge of the slip road beside them.

Two and a half metres of missing road that wasn't missing

Straight after that fix, the check that every detour returns to where it claims started failing by about two and a half metres — on every fork, on every route.

The roads were fine. The test was measuring to the centre line while the roads had just been taught to rejoin at the edge, so it was reporting exactly the offset it had failed to account for. Measured properly, all ten forks close to within a ten-thousandth of a metre. Worth the note because the instinct on a failing check is to go looking in the thing being tested, and here the newer, less-examined code was the test itself.

A generator that produced routes that didn't match their own spec

The design brief says a first-level route runs about eight kilometres and each level adds four to six. The first batch put the Old City at 2.3 km growing by 2.7, and the flyway at 9.8.

The lengths were an accident of adding up hand-written segment lists, so nobody was ever checking them against the brief. Now each level is written for character and then padded to an explicit target — and the tool refuses outright if what's been written already overshoots. It refused immediately on the flyway: 8036 metres of road against an 8000 metre target. A generator that argues with you is better than one that quietly produces something out of spec.

A fourth memory test that measured the wrong thing

Another check that "this creates no litter" failed — passing on its own, failing when run after others. The third one of these, across two stages of work.

Three of the same failure is a pattern, not luck. All of them worked by watching total memory rise, which measures a consequence, through a channel every other test shares, against a threshold that was a guess. Replaced with the actual claim: that the same objects and the same storage survive the loop, checked by identity, plus a scan of the code itself for the constructs that create things. Both are exact, and both fail on the change that breaks them rather than on whichever unlucky run notices.

What we went with, and why

Every detour is the same shape: four equal arcs, bending right, left, left, right. Because it's symmetrical, the turns cancel — it ends up pointing the way it started and exactly back on the line it left, having bulged out to one side and returned. It is longer than the straight it replaced by a ratio that depends only on how sharply it bends, not on how big it is. So you pick the bend angle to get the length ratio you want, then pick the size to fit the space. That is what turns "draw a plausible loop and hope" into two numbers you solve for. All ten close to within a fraction of a millimetre.

For "who is ahead", the answer is that distance travelled and race position are two different quantities that had been sharing one number. A rider on the long way round covers more ground for the same amount of race. So a separate reading maps each route onto the stretch of main road it replaces — that's called normalisation — and standings are sorted on that, never on raw distance. Both routes reach the join at precisely equal progress, by construction.

Difficulty levels are stored as deltas: a level names the one below it and lists only what it adds. Level five of a route is five short files, not one long one, and fixing a corner in level one fixes it in all five.

What this costs: every fork in the game is the same shape. A road network with genuinely irregular junctions is not expressible this way, and the honest reason it's this shape is that this shape can be solved. It also means both roads of a split are drawn at once, which is more to draw at exactly the moment there is most to look at.

We didn't let the tool that solves the geometry run as part of the game, because then the tracks would only exist while the tool did. It writes the files, the files are checked in, and the game validates them on load like any other data — so a track can be edited by hand later without the tool being involved at all.

Show me in the code

src/core/sim/step.ts → stepRoute()

Deciding which road you took, and putting you back on the main one afterwards. 

function stepRoute(rider: Rider, track: Track, previousS: number): void {
  if (rider.pos.branchId === MAIN_BRANCH) {
    for (let i = 0; i < track.branches.length; i += 1) {
      const branch = track.branches[i];
      if (!branch) continue;
      // Only at the tick the rider crosses the split, never after.
      if (previousS >= branch.forkS || rider.pos.s < branch.forkS) continue;

      const first = branch.path.segments[0];
      if (!first || first.curvature === 0) continue;
      const side = first.curvature > 0 ? 1 : -1;

      // Committed to that side of the road at all?
      if (rider.pos.t * side < FORK_CAPTURE_T) continue;

      // And actually alongside the branch's mouth. `t` on a branch is measured
      // from the branch's own centreline, so entering is a translation, not a
      // snap — a rider hugging the outside edge of a wide road is exactly on
      // the outside edge of the slip road leaving it.
      const local = rider.pos.t - branch.entryT;
      if (Math.abs(local) > first.halfWidth + first.shoulder) continue;

      rider.pos.t = local;
      rider.pos.branchId = i + 1;
      return;
    }
    return;
  }

  const branch = track.branchById(rider.pos.branchId);
  const end = branch.forkS + branch.path.length;
  if (rider.pos.s >= end) {
    rider.pos.s = branch.rejoinS + (rider.pos.s - end);
    rider.pos.t += branch.entryT;
    rider.pos.branchId = MAIN_BRANCH;
  }
}
  1. The choice is made once, on the single tick you cross the split, and never revisited. A fork you can wander back onto fifty metres later is not a fork.
  2. Which side the branch leaves from is read from the branch's own first bend rather than stored as a separate field. Nothing to keep in sync, and the rule matches what the split looks like on screen.
  3. Two conditions, not one. This is "did you commit to that side of the road at all" — a rider drifting a few centimetres off centre has not chosen anything.
  4. And this is "are you actually beside the opening". Together they are what the earlier version got wrong by asking only the first.
  5. The line that turns a jump into a change of viewpoint. Sideways position on a branch is measured from that branch's own centre, so entering subtracts the offset instead of dragging the rider to a new place.
  6. Rejoining carries the overshoot across rather than discarding it, so a rider who crossed the end mid-tick keeps the ground they covered. Dropping it would cost a few centimetres per fork — invisible once, and a real bias over a career.

Say it out loud

Twenty-five tracks — five routes, five tiers — stored as deltas, so a tier names the one below it and lists only appended segments, and the extends chain resolves at load. The interesting constraint is the forks: a branch has to close geometrically within half a metre and be within five percent of the span it replaces, and those fight, because any curve is longer than its chord. The shape that solves it is four equal arcs — right, left, left, right — which is symmetric, so it returns to the line it left facing the same way, and its length ratio is phi over sine phi, independent of radius. So you solve phi for the ratio and pick the radius for the space. All ten close to under a millimetre. The other half is that distance travelled and race position had been sharing one number, so progress normalises each branch onto the main span it replaces and standings sort on that — both routes hit the rejoin at exactly equal progress. Fork rendering needed almost nothing, because branch chunks carry their span in main-path terms and the existing numeric cull just works on them.

Phase 04

Traffic and hazards

The road stops being empty: buses, autos, cars and trucks that drive themselves, oil and potholes and cows that don't move, and a crash you have to get up from.

What we were trying to do

Up to this point the roads were real but deserted. You could ride five Delhi routes at five difficulty levels and never meet another vehicle. This phase fills them.

Three things had to arrive together. Moving traffic: city buses, autos, cars and trucks that pick a lane, hold a speed, slow down behind something slower, and occasionally change lane. Things lying in the road that don't move: oil, sand, potholes, road works, barricades, stray dogs, cows. And what happens when you hit any of it — the rider comes off, the bike slides, and after a few seconds you are back on it, having lost time.

The bar was not "there are vehicles on screen". It was that the traffic had to behave like traffic for ten minutes without a single vehicle ever occupying the same piece of road as another one, and without the game slowly eating memory while it did.

Why this was hard

The difficulty was not writing traffic. It was one line in the acceptance criteria: no two vehicles are ever closer than their combined size, measured properly along the curve of the road rather than by subtracting two numbers.

"Never" is a much stronger word than it looks. Traffic that usually keeps its distance is easy. Traffic where the guarantee cannot be broken means every single thing that can move a vehicle sideways has to ask permission first — and the last one we found was not a decision the traffic made at all.

Roads in this game change width. The Ring Road goes from three lanes to four. When it does, the middle of lane two moves: it was 6.67 metres right of the centreline, now it is 2.75. Nothing decided anything. The road changed shape underneath the vehicle and the code obediently dragged it four metres sideways, straight through whatever was there. The rule we had written was "ask before you change lane", and this was not a lane change.

What we tried that didn't work

Pushing overlapping vehicles apart

The first instinct when two vehicles are too close is to move them apart. It works for one pair and creates the next one: the car you pushed backwards is now inside the car behind it, which gets pushed into the one behind that. On a busy stretch a single correction rippled down a queue of eleven vehicles, and the queue visibly shunted.

Position is the wrong thing to correct, because correcting it is a change nothing else has agreed to. The fix was to limit speed instead: a vehicle is not allowed to go fast enough to close the gap below the minimum. Nothing is ever moved, so nothing is ever shoved, and the guarantee holds by construction rather than by repair.

Diagnosing the last overlap from the wrong cause

Four attempts in, vehicles still overlapped by up to 79 centimetres, and the working notes confidently blamed lane changes crossing through each other. A fifth fix for that cause was already half-written. Dumping every offending pair at the moment it happened showed something else entirely: neither vehicle was changing lane, and a third of the cases were oncoming traffic sitting exactly on the centreline of a road that had narrowed to a single lane.

The lane-change theory explained a plausible failure that was not the failure occurring. Two real causes were hiding behind it — lane centres jumping when the road changes width, and new vehicles being placed before the code knew which side of the road they belonged on. Writing the fifth fix would have added complexity to the wrong function and left the number at 79 centimetres.

A complete hazard system that nothing could ever hit

Hazards were built, tested, and correct: seven kinds, collision resolution, crash and remount. Then a test that rode the actual routes looking for actual hazards found zero. Not a bug in the code — the twenty-five route data files simply contained no hazards. The entire feature was unreachable and every test of it had passed.

Every test used a hand-built track with hazards placed in it, so every test proved the machinery worked and none proved the game used it. Two hundred and four hazards went into the route files, and the missing test — ride the real routes, count what you meet — now exists so the gap cannot reopen quietly.

Three timing tests that were measuring the computer

Tests that check something is fast enough kept failing when the whole suite ran and passing when run alone. The most recent one timed out only when coverage measurement was switched on.

They were reading how busy the machine was, not how fast the code was. Two now take the fastest of three attempts — interference can only ever make a timing look worse, never better, so the best sample is the least contaminated one. The third was genuinely slow work being held to a five-second default, so the limit moved rather than the work.

What we went with, and why

Every sideways movement now goes through one function that answers a single question: where across the road does this vehicle want to be? It starts from the middle of its lane, and on a two-way road it refuses to return anything that would put the vehicle's body over the centreline — half its own width plus twenty centimetres of clearance, on its own side. Spawning uses it, lane changes use it, and drifting towards the lane centre uses it, so there is one place where the rule lives instead of three.

Two supporting changes make that hold. A vehicle only counts as "in front of me" if it shares my lane or physically overlaps me sideways — a bus straddling two lanes is now visible to both. And drifting towards a lane centre is checked for space first; a vehicle that cannot get there stays where it is, and one that has been squeezed off the road entirely is recycled rather than fudged back on.

What this costs: traffic is slightly more timid than real traffic. A vehicle that wants to move over and cannot simply waits, so on a genuinely packed road you see a little more patience than a Delhi driver would ever show. The overlap distance went from 79 centimetres of interpenetration to at least 61 centimetres of clear air on every route tested, which is the trade we wanted.

We didn't use a physics engine, which would have solved vehicle-versus-vehicle overlap for free. It would also have made the simulation depend on floating-point behaviour we do not control, and this game guarantees that the same seed and the same inputs produce the same race on every machine. That guarantee is worth more than the convenience.

Acceptance criteria
The list of things that must be true before a piece of work counts as finished.
Pre-agreed, testable conditions defined before implementation, each of which must be demonstrated rather than asserted before the work is accepted.
Branch
A place where the road splits in two and joins up again later.
An alternate path with its own distance measurement, identified by a branch id carried alongside every position, so two points on different paths are never compared as if they were on one.
Centreline
The imaginary line down the middle of the road.
The reference curve from which all track-space positions are measured; distance along it is s and offset across it is t.
Code coverage
How much of the code the tests actually run.
The proportion of lines, branches or functions executed during a test run; high coverage proves code was exercised, not that it was exercised correctly.
Determinism
Same start, same actions, same result — every time, on every computer.
The property that a simulation's entire state is a pure function of its seed and input sequence, which requires avoiding operations whose results are permitted to differ between platforms.
Float32 / single precision
A way of storing numbers that trades accuracy for space.
A 32-bit IEEE-754 floating-point value carrying roughly seven significant decimal digits, so a coordinate a kilometre from the origin is representable only to about a tenth of a millimetre.
Frustum culling
Not bothering to draw things that are behind you.
Testing each object's bounds against the camera's visible volume and skipping the draw call for anything entirely outside it.

A single geometry and material submitted once with a per-copy transform array, so the number of draw calls stays at one regardless of the number of copies.
Interpolation

Blending between the two most recent simulation states by the fraction of a tick elapsed, so rendering at any refresh rate stays smooth over a fixed-rate simulation.

Show me in the code

src/core/sim/traffic.ts → targetT()

Fourteen lines, and the only answer in the codebase to "where across the road should this vehicle be". Spawning, lane changing and lateral drift all call it, which is why the road-widening bug could be fixed once rather than three times. 

function targetT(
  track: Track,
  vehicle: TrafficVehicle,
  lane: number,
  lanes: number,
  halfWidth: number,
): number {
  const want = laneCentre(lanes, lane, halfWidth);
  if (track.segmentAt(vehicle.pos.s, vehicle.pos.branchId).oneWay) return want;

  const clear = TRAFFIC_SIZES[vehicle.kind].width / 2 + CENTRELINE_MARGIN;
  return vehicle.oncoming ? Math.min(want, -clear) : Math.max(want, clear);
}
  1. The lane is passed in rather than read from the vehicle, so the same function can answer "where would I be if I moved to lane three" without building a copy of the vehicle. Copying an object inside the simulation loop would allocate memory sixty times a second, which the project forbids.
  2. The starting point: the middle of the requested lane. This is the value the old code used directly, and it is correct — it is just not always reachable.
  3. On a one-way road there is no oncoming traffic and no centreline to respect, so the lane centre is the final answer. The flyway is one-way, which is most of why it is the fastest route in the game.
  4. Clearance is measured from the edge of the vehicle, not its middle, because a bus and an auto need different amounts of room to sit legally in the same lane.
  5. The clamp. Oncoming traffic may never be further right than its own clearance, ordinary traffic never further left. Because every caller goes through here, a road that changes width mid-corner can no longer drag a vehicle across the divider — the lane centre may jump, but the returned value cannot.

Say it out loud

The traffic was straightforward until the non-overlap guarantee. I'd written it as a constraint on lane changes, and it still failed by seventy-nine centimetres, so I dumped every offending pair at the moment of contact — and neither vehicle was changing lane. Roads in this game change width, and when the Ring Road goes from three lanes to four the centre of lane two moves four metres. The vehicle wasn't making a decision at all; the road moved underneath it. So every lateral movement now goes through one function that clamps to the correct side of the centreline, and drifting is gated on there being room to drift into. It went from seventy-nine centimetres of overlap to sixty-one centimetres of clear air, and the fix is structural — there's no tuning constant holding it up.

All of it

In 90 seconds

The whole project on one page: what it is, how it is put together, and the three choices everything else follows from.

The elevator version

Rashta is an arcade motorcycle combat racer set in Delhi at night, written from scratch in TypeScript with no game engine, no physics engine and no UI framework. It ships as a web page of about a hundred and forty kilobytes. The interesting part is a constraint I set at the start: the simulation is bit-exactly deterministic, so the same seed and the same inputs produce the same race on every machine. That rules out a physics engine, and it rules out sine and cosine anywhere the simulation can reach, because the standard does not require two browsers to agree on them. So the game holds every position as distance along the road rather than a point in space, does all its trigonometry once when a track loads, and the simulation reads tables. Five routes, five tiers, city traffic, hazards, and a crash you have to get up from.

Built so far: the road, the bike, the loop, twenty-five routes, city traffic, hazards, crashes, and enough renderer to ride through all of it. Rivals, combat, police, career and reputation are Phases 5–9; the desktop build is Phase 10.

The three decisions that most shaped the project

  1. Positions are distances along the road, not points in space.

    Everything in the simulation is held as s, metres travelled along the centreline, and t, metres left or right of it. World coordinates are computed at render time and never stored. This is why "who is winning" is a comparison of two numbers, why the road can bend without anything in the simulation knowing, and why a track that forks in two can be ranked at all.

    What it costs: distance between two points is no longer subtraction. Two vehicles a metre apart on the inside of a bend are not a metre apart, so there is a dedicated function that corrects for curvature, and every piece of code that wants a real distance has to remember to call it.

  2. The simulation is bit-exactly deterministic, which means no sine and no cosine.

    Addition, multiplication and square root are guaranteed by IEEE-754 to give identical answers on every conforming engine. The trigonometric functions are explicitly not. One cosine inside the simulation downgrades "the same on every machine" to "the same on this browser build", so all trigonometry happens once when a track loads, and the simulation reads precomputed tables and interpolates between them.

    What it costs: real work. Measuring distance along a curve needs a sine, so it uses a four-term series expansion instead, with a defined fallback past the range where the series is trustworthy. A physics engine was never an option, which means vehicle-versus-vehicle separation had to be built by hand and took five attempts to get right.

  3. The simulation is forbidden from importing the renderer.

    src/core/ cannot import Three.js, the DOM, the input layer or the audio layer — not by convention but as a rule the build enforces. The consequence is that the entire game is testable without a graphics card: two hundred and ninety-seven tests run in under a minute, including ten simulated minutes of tier-five traffic checked pair by pair for overlap.

    What it costs: duplication and discipline. There is a small hand-written vector type in core because importing Three.js's would break the rule, and every value the renderer needs has to be read out of core rather than reached for. Anything that wants to be in both places has to be designed to be in neither.
